3 · Seguridad: JWT y control por rol5:30 – 9:30 · Sergio

Teoría (40 s): la API no guarda sesión. El cliente cambia su contraseña por un token una sola vez y después manda el token. El token tiene tres partes: cabecera, contenido (usuario, rol, vencimiento) y firma. La firma es un HMAC con un secreto que sólo tiene el servidor: cualquiera puede leer el token, nadie puede modificarlo.

Demostración (1:40): python pruebas/demo_api_jwt_409.py --sin-cancelar y recorrer la salida:

  1. Sin token → 401.
  2. Login → 200 con el token. Señalar el contenido decodificado: sub, rol, exp.
  3. Con el token → 200. Con el rol cambiado a mano → 401: la firma ya no coincide.
  4. Token válido de administrativo → 403. Autenticado, pero sin permiso.

Código (1:30):

  • seguridad/CodificadorJwt.java: emitir (línea 56) arma el contenido y firma; validar (línea 69) exige HS256, compara la firma y revisa el vencimiento.
  • seguridad/MecanismoAutenticacion.java, autenticarApi (línea 97): lee Authorization: Bearer, valida y le pasa usuario y rol al contenedor.
  • api/TurnosResource.java (línea 74): @RolesAllowed("PACIENTE"). El 403 no lo decide nuestro código: lo decide el contenedor con esa anotación.
«401 es "no sé quién sos"; 403 es "sé quién sos y no podés". El rol viaja firmado en el token, por eso no hace falta ir a la base en cada pedido.»

Preguntas probables, por integrante

Sergio

  • ¿Dónde se guarda la sesión del JWT? En ningún lado: el token lleva todo y la firma lo garantiza.
  • ¿Y si me roban el token? Sirve hasta que vence (30 minutos). No se puede revocar antes: es la limitación declarada.
  • ¿Por qué la web no usa JWT? JSF guarda el estado de las vistas en el servidor: la sesión existe igual. El JWT está en la API, que es sin estado.
  • ¿Por qué lo hicieron a mano? HS256 son pocas líneas con javax.crypto; las podemos explicar y probar.
  • ¿Qué es alg: none? Un token que dice no tener firma. Lo rechazamos y hay un test.

Máximo

  • ¿Por qué DAO? Para que cambiar una consulta no toque la lógica de negocio.
  • ¿Qué hace @Version? Bloqueo optimista: si dos transacciones modifican el mismo turno, la segunda falla.
  • ¿Por qué RLS si la aplicación ya tiene roles? Porque Supabase publica las tablas por su propia API: sin RLS había otra puerta a los datos.
  • ¿Dónde están las credenciales de la base? En la configuración de WildFly, no en el repositorio.

Agustín

  • ¿Por qué State y no un switch? Con el switch la regla queda repartida y un servicio nuevo puede olvidarla. Acá es imposible saltearla.
  • ¿Por qué 409 y no 400 o 422? El pedido está bien formado y los datos son válidos; choca con el estado del recurso.
  • ¿Qué pasa en la base con el 409? Nada: la excepción revierte la transacción y no se publica el evento.
  • ¿Por qué la cancelación es un servicio aparte? El de turnos tiene estado (el hold) y la API es sin estado. ProcesoCancelacionTurno lo usan la web y la API.
  • ¿Cola o tópico? Cola cuando lo procesa uno solo (la autorización); tópico cuando interesa a varios (el turno confirmado).
  • ¿Y si un mensaje llega dos veces? Cada suscriptor registra el evento procesado y descarta el repetido.

Cualquiera

  • ¿Qué cambiarían? Restituir el monitor de eventos y agregar el bloqueo de intentos de ingreso.
  • ¿Qué hizo la IA y qué ustedes? Lo declarado en el informe; por eso cada uno explica su código y su test.
